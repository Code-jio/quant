### R01 · P1 · 注销或切换账户后，权益历史仍混入新账户

位置：[账户清理](D:/mine/quant/back_end/src/api/__init__.py:528)、[仪表盘计算](D:/mine/quant/back_end/src/api/__init__.py:1101)。

`clear_main()` 清理引擎、策略和权重，没有清理 `_equity_curve`。仪表盘直接使用这份进程级曲线，没有校验账户归属。

复现：A 账户余额 100000，留下 10 个收益为 1234 的样本；通过真实 API 注销，再登录余额 10000、收益为 0 的测试账户 B。B 的 `/dashboard/metrics` 返回 `account_id=B`，曲线仍含 A 的 1234，并显示 **90% 最大回撤**。这既污染绩效，也让下一位登录者读到上一个账户的历史收益。旧 cookie 被撤销的问题已经修复，本项是另一条数据残留路径。

建议：账户切换时原子清理账户派生状态，曲线按 broker/account/generation 分区；广播任务也应携带账户代次，拒绝将旧代次计算结果写入新账户。验收须覆盖直接切换和注销后重新登录。

证据：[backend-probes.json](D:/mine/quant/docs/evidence/recheck-20261005/backend-probes.json)，键 `cross_account_equity_after_logout`。关联原 Q04、Q52，不能将账户隔离整体视为完成。

### R02 · P1 · 网页登录缺少保证金配置通路，正常开仓始终被拦截

位置：[登录请求](D:/mine/quant/front_end/src/views/LoginView.vue:340)、[API 配置来源](D:/mine/quant/back_end/src/api/__init__.py:1603)、[合约保证金映射](D:/mine/quant/back_end/src/trading/vnpy_gateway.py:319)、[开仓门禁](D:/mine/quant/back_end/src/trading/engine.py:195)。

页面没有 `contract_margin_rates` 输入或提交字段；API 默认收到 `{}`，也没有在这条登录路径合并本地配置。适配器只从该映射读取保证金率，不从合约事件推导。最终所有从页面登录的合约 `margin_rate=None`，即使账户、报价和连接正常，开仓仍被拒绝；内置策略的手数计算也会得到 0。

复现：调用真实合约转换方法，接入已连接的 FakeGateway，字段齐全但保证金率为空时限价开仓被拒，原因 `Broker margin rate/account fields must be verified before opening`，网关收到 0 单。同一测试合约补入经核实的 0.1 后，同一信号成功到达测试网关，返回 `ORDER_1`。

建议：补齐受校验、按账户保存的保证金配置入口，或接入经核实的柜台保证金率查询；登录后明确展示未满足的开仓条件。继续保留未知保证金时拒绝开仓的门禁。文档声称可用本地配置，并不能解决当前 Web/API 路径未读取配置的问题。

证据：[backend-probes.json](D:/mine/quant/docs/evidence/recheck-20261005/backend-probes.json)，键 `margin_missing_from_browser_login`，包含正向对照；页面缺字段通过代码核实，未进行真实柜台登录。关联原 Q18、Q19 的端到端可用性。

### R03 · P1 · 策略指标窗口错位，可能提前产生突破信号或延迟均线信号

位置：[回测历史切片](D:/mine/quant/back_end/src/backtest/engine.py:139)、[突破窗口](D:/mine/quant/back_end/src/strategy/strategies/breakout.py:39)、[均线窗口](D:/mine/quant/back_end/src/strategy/strategies/ma_cross.py:43)。

引擎约定 `strategy.data` 只包含当前回调之前的已完成行情。内置策略仍以“历史里含当前 bar”的索引方式计算：突破策略又向前减一，漏掉最新已完成 bar；均线和 RSI 使用上一根指标，却用当前回调价格构造信号。

固定样本复现：

- 突破窗口为 2，历史高点为 `[110,110,200]`，当前收盘 150。正确最近两根最高价为 200，当前没有突破；实际产生 `long` 信号。
- 快慢均线为 1/2，历史收盘 `[100,100,100]`，当前收盘 110 出现金叉却无信号；下一根收盘跌至 90、已经死叉，实际才发出 `long` 信号。

建议：明确完成 bar 在 `on_bar` 计算中的归属；MA/RSI 将当前完成 bar 纳入指标，突破窗口取当前 bar 之前最后 N 根。保持订单最早下一根成交的规则，避免用修复时点错位的方式引入同 bar 撮合偏差。用逐 bar 预期信号测试比较回测与实盘回放。

证据：[backend-probes.json](D:/mine/quant/docs/evidence/recheck-20261005/backend-probes.json)，键 `breakout_excludes_latest_completed_bar`、`moving_average_uses_previous_bar_cross`。属于原 Q09 已知时点问题的进一步复现，非完全新增问题。

### R04 · P2 · 快照失败后，已收到的订单推送被留在缓冲区

位置：[快照失败分支](D:/mine/quant/front_end/src/composables/useOrderBookWs.js:112)、[增量缓冲](D:/mine/quant/front_end/src/composables/useOrderBookWs.js:120)。

`loading=true` 时订单和持仓消息放入 `buffered`，只有快照成功才重放。快照请求失败只关闭 loading、显示 stale，没有应用这些消息，也没有安排自动补偿快照。

复现：初始 O1=`submitted`；发起刷新；刷新期间收到 revision=2 的 O1=`filled`；刷新超时。组件继续显示 `submitted`。若终态没有再次推送且连接保持正常，会一直等到后续成功刷新才恢复。页面确实显示过期警告，因此没有把此项描述为“无提示的实时数据”。

建议：失败后按最后成功快照的 revision 重放有效增量，保留 stale 标记并有限重试补齐快照；覆盖重叠刷新、失败、迟到消息及已成交终态。

证据：[frontend-probes.txt](D:/mine/quant/docs/evidence/recheck-20261005/frontend-probes.txt)。定向回归断言 `filled` 实际得到 `submitted`，**失败已确认**；原有前端 11 项测试仍通过。关联原 Q44，现有补快照实现尚未覆盖失败分支。

### R05 · P2 · RSI 极端行情计算错误，且前后端口径不一致

位置：[后端 RSI](D:/mine/quant/back_end/src/watch/kline.py:129)、[前端 RSI](D:/mine/quant/front_end/src/workers/indicatorMath.js:60)。

后端把零损失换成 NaN，随后统一填为 50，导致持续上涨时 RSI 错算为 50。前端用简单滚动平均，后端用指数平滑；前端还将完全横盘的 RSI 算为 0，而后端选择 50。

复现：收盘从 100 连续涨到 129，后端输出 **50**，前端约 **100**；30 根收盘都为 100，前端输出 **0**。同一段涨跌混合数据，后端 58.023800，前端 58.333333。持续上涨的 50 是明确计算错误，其他数据也没有一致的算法约定。

建议：统一 RSI 定义、初值和预热范围，显式处理“有涨无跌→100、有跌无涨→0、完全不变→约定中性值或未知”；用同一套固定样本校验服务端、Worker 和策略。当前图表载入后会使用 Worker 重算，因此本项没有声称初始画面必然发生跳变。

证据：[backend-probes.json](D:/mine/quant/docs/evidence/recheck-20261005/backend-probes.json) 的 `server_rsi`、[frontend-indicators.json](D:/mine/quant/docs/evidence/recheck-20261005/frontend-indicators.json)。

### R06 · P2 · 无效风控配置返回 HTTP 500，缺少参数级反馈

位置：[更新风控配置](D:/mine/quant/back_end/src/api/__init__.py:1916)。

登录接口会将 `RiskConfig.from_mapping` 的校验错误转成 422，但 PUT `/risk/config` 直接调用 `configure_risk`，没有处理相同的 ValueError。有效登录会话提交 `{"risk":{"max_order_volume":0}}`，实际响应 **500 / Internal Server Error**，无法向调用方说明哪个参数无效。

建议：在修改引擎和持久化之前完成整份配置验证，将无效输入返回 422 和明确字段信息；失败时确认当前配置及持久配置不变。这是错误分类和可诊断性问题，本轮未发现该样本会破坏原配置。

证据：[backend-probes.json](D:/mine/quant/docs/evidence/recheck-20261005/backend-probes.json)，键 `invalid_risk_config_response`。
